# Agenda : règles détaillées

Valables aussi pour `src/pages/Evenements.tsx`, `EvenementDetail.tsx`, `ProposerEvenement.tsx`, `AdminEvenements.tsx` et `src/lib/events.ts`.

- **Proposition :** côté site, l'enregistrement d'une proposition ne doit pas demander la ligne en retour (le membre ne peut pas la relire avant publication).
- **« Je viens » :** les inscriptions vont dans `evenement_inscriptions`. Le public ne voit que le nombre (`nb_venues`), l'organisateur·ice voit la liste (`mes_venues`).
- **Types :** codes figés en base (contrainte), libellés dans `EVENT_TYPES`. Le code `apero_ecoute` désigne le rendez-vous mensuel affiché « Atelier-écoute », car renommer un code casserait les fiches existantes.
- **Questions fréquentes :** `evenements.faq`, écrites par un admin seulement (les déclencheurs l'effacent pour un membre), sinon `faqParDefaut` (`src/lib/faqEvenement.ts`), pour que les réponses restent sous le contrôle de l'équipe.
- **Titres et textes :** affichés via `readableTitle`, émojis retirés à l'enregistrement par `sansEmojis`, pour garder une casse homogène quel que soit l'auteur·ice.
- **Dates :** toujours à l'heure de Paris (`heureParis`, `horairesParis`, `dateParis`, `isoParis`). Plusieurs jours via `surPlusieursJours` / `jourCourt` / `dateLongue` : une fin avant 6 h compte pour la veille.
- **Partage :** toujours l'adresse publique `/agenda/:slug` (une adresse de fonction serveur répond en texte brut). Texte et vignettes (1200×630, 1080×1080) faits dans le navigateur par `src/lib/partageEvenement.ts`.
- **L'Onde et Instagram :** la case « Ajouter au prochain numéro » passe par `onde_agenda_basculer` / `onde_agenda_etat` (admins seulement, brouillon le plus ancien, jamais un numéro publié, 8 événements par bloc), via `src/lib/agendaOnde.ts`. Le compte Instagram de l'organisateur·ice vit à part dans `evenements_instagram` (admins seulement), pour qu'il ne soit jamais lisible par le public. Post et story Insta (canvas) et légende sont faits dans le navigateur par `partageEvenement.ts` (`PostInsta`), rien n'est publié automatiquement.
- **Veille automatique :** une connexion serveur de confiance (sans compte, ni visiteur ni compte connecté) peut insérer un événement `origine = 'pds'`, toujours forcé en relecture par `guard_evenements` (`propose_par` vide, `propose_par_nom` gardé, badge « Proposé par … » dans l'admin), pour qu'aucune insertion automatique ne publie seule. L'affichage public lit `statut = 'publie'` ; `publie` reste une copie tenue par les déclencheurs.
- **Organisateur affiché :** uniquement quand on le sait — `propose_par_nom` porté par un compte membre (`origine = 'membre'`) → « Proposé par … », sinon événement de l'association (`origine = 'pds'` sans nom et case décochée) → « Organisé par … ». `sansOrganisateur` (dans `useHomeData`) décide de ne rien afficher : événement venu de la veille (`origine = 'pds'` avec un nom, sans compte) ou case `organisateur_exterieur` cochée dans l'admin (« Ce n'est pas PDS qui organize »). Rien n'est alors affiché sur la fiche, dans l'agenda, dans L'Onde ni dans les données structurées. La case est forcée à `true` par `guard_evenements` sur une insertion serveur, forcée à `false` sur une proposition de membre, et gardée à `OLD` par `guard_evenements_update` pour un membre : seul un admin la change. Les filtres « Les rendez-vous PDS » / « Proposés par les membres » laissent ces événements dans « Tous » seulement.
- **Mise en avant :** sur `/agenda`, un vrai rendez-vous de l'association (`estRendezVousPds` : PDS sans `sansOrganisateur`) est affiché encadré, en plus grand, avec son image (`EventRow vedette`), pour que la mise en avant suive la même règle que la mention « Organisé par ».
