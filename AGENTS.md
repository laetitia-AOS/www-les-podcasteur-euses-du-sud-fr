# Règles techniques du projet

- Les couleurs et polices passent uniquement par les variables de `src/index.css` (préfixe `--pds-`) et `tailwind.config.ts` ; les anciennes variables (tc, bleu, ink…) sont des alias à garder tant que des pages non refondues les utilisent.
- Les classes partagées des boutons, du conteneur et des fonctions de mise en forme (noms, villes, durées, dates) vivent dans `src/lib/pds.ts` : les réutiliser plutôt que les recopier, pour garder un style identique d'une page à l'autre.
- Les épisodes sont enregistrés dans la table `episodes` par la seule fonction `sync-episodes` (tâche planifiée toutes les 6 h, une lecture au plus toutes les 5 h 30 via `demarrer_sync_episodes`), lisibles par tous uniquement pour les podcasts visibles de membres à jour (`episodes_visibles`) ; le site les lit via `src/lib/episodes.ts`. La lecture des flux passe par `_shared/flux.ts` (https public seulement, 8 s, 5 Mo) pour éviter tout détournement du serveur. L'ancienne fonction `podcast-episodes` ne sert plus qu'à la version publiée précédente.
- Le lecteur audio est un contexte global (`PlayerProvider` dans App) avec la barre `PlayerBar` hors des routes, pour que l'écoute continue pendant la navigation.
- Les sections de l'accueil sont dans `src/components/home/`, chacune autonome et alimentée par `useHomeData.ts`.
- L'inscription vit sur la page Adhérer : étapes dans `src/components/adherer/`, listes, tarifs et envoi d'images dans `src/lib/inscription.ts`. Une personne = une ligne `podcasts` par podcast (mêmes infos de profil et même e-mail), pour garder la base existante intacte.
- La photo de profil d'une personne est `photo_profil_url` ; `vignette_url` reste la pochette du podcast (ou la photo pour les fiches sans podcast). L'annuaire passe par `profilePhotoFor`, jamais directement par la pochette.
- L'espace membre (`src/pages/MonPodcast.tsx`, blocs dans `src/components/espace-membre/`) lit l'adhésion, les messages reçus et les événements proposés via les fonctions `mon_adhesion`, `mes_demandes`, `mes_evenements` (limitées à l'e-mail connecté), pour ne pas modifier les règles d'accès de ces tables. Un paiement à un autre nom ou une autre adresse est relié à un membre par la table `adhesion_rattachements` (écriture admin seulement), prise en compte par `mon_adhesion`, sans modifier la ligne HelloAsso d'origine.
- Les formulaires publics sont vérifiés, nettoyés et limités (5 envois/heure/adresse) par des déclencheurs `guard_*` en base, pour que la règle tienne même hors du site ; les clients affichent le motif via `messageServeur`. Messages aux membres et devis passent uniquement par la fonction `contact-membre` (une insertion groupée = un envoi).
- Seuls le webhook HelloAsso (serveur) et les admins écrivent dans `adhesions`. Le webhook relit la commande chez HelloAsso (`_shared/helloasso.ts`) ; si HelloAsso refuse la lecture, le paiement est enregistré `a_verifier`, ce qui n'active aucune fiche tant qu'un·e admin ne le passe pas en `active`.
- Les exports tableur passent par `toCsv` (`src/lib/csv.ts`), qui neutralise les formules.
- Un·e visiteur·ice non connecté·e n'envoie jamais d'image directement : `uploadImages` passe par la fonction `envoi-image` (type réel, poids, limite par adresse), qui range l'image dans le dossier privé `images-en-attente`. Son adresse publique définitive ne répond qu'après validation admin (`valider-images`, appelée aussi en validant une fiche ou en publiant un événement). Les personnes connectées écrivent dans leur propre dossier.
- « Je cherche / J'apporte » sont des codes (`cherche_choix`, `apporte_choix`, liste `COLLAB_CHOIX` dans `src/lib/inscription.ts`, vérifiés par `guard_podcasts_collab`) plus une précision libre ; les anciennes colonnes `cherche_collaboration` / `peut_apporter` sont des archives (encore écrites par le formulaire des structures). L'annuaire filtre sur `apporte_choix`.
- Messages, devis et propositions de collab sont une seule boîte (`contact_requests.type`), écrite uniquement par `contact-membre` et lue par le membre via `mes_demandes` / `marquer_demande_lue` ; aucun accès direct visiteur ou membre à la table.
- Les détails des studios et structures vivent dans `fiches_lieux` (1 ligne par fiche, sans e-mail, contrôlée par `guard_fiches_lieux`, modifiable par le lieu connecté ou un admin) ; le formulaire unique est `src/components/studios/LieuEditor.tsx` (espace membre et admin). Les pages publiques lisent les colonnes de `LIEU_COLUMNS`, jamais l'e-mail ni le téléphone.
- Les devis passent uniquement par la fonction `demande-devis` : le serveur choisit les studios destinataires, enregistre la demande dans `demandes_devis` (limite par adresse dans `guard_demandes_devis`) et une ligne `contact_requests` de type devis par studio.
- Agenda : `evenements.statut` (en_relecture / publie / refuse) est la seule source de vérité, `publie` n'est qu'une copie gardée par les déclencheurs `guard_evenements*`. Seuls les membres à jour proposent (forcé en relecture), seul un admin change le statut ; l'auteur·ice est dans `evenements_proposeurs` (privé). Les venues (« Je viens ») vont dans `evenement_inscriptions` : public = `nb_venues` (nombre seul), organisateur·ice/admin = `mes_venues`. Le sitemap des événements est servi par la fonction `sitemap-evenements` (déclarée dans robots.txt). Un insert de proposition côté client ne doit pas demander la ligne en retour (la lecture n'est autorisée qu'après l'enregistrement de l'auteur·ice).
- Un membre modifie sa fiche `podcasts` mais jamais `valide`, `email` ni `created_at` (déclencheur `guard_podcasts_update`) : seule l'adhésion ou un admin publie une fiche.
- Adhésion : `adhesions.date_echeance` (déclencheur `adhesion_echeance`, 1 an après confirmation, renouvellement ajouté à l'échéance en cours) et `formule` (personne/studio, d'après la formule HelloAsso payée) font foi ; `membre_a_jour` lit l'échéance. Une fiche n'est publique que si `podcast_visible(id)` (validée + membre à jour) : la règle de lecture publique de `podcasts`, `episodes_visibles`, `lieu_visible` et `contact-membre` passent par elle, sans tâche programmée.
- Chiffres des membres : écrits seulement par la fonction `compter-stat` (empreinte = sel secret `STATS_SEL` + jour + IP, jamais l'IP en clair, purge 48 h) via `compter_stat` (service seulement) ; lus par `mes_stats()` limité à l'e-mail connecté. Côté site, appeler `compterStat` de `src/lib/stats.ts`.
- La liste admin des membres passe par `admin_membres()` (vide hors admin). La suppression des données d'un membre passe uniquement par la fonction `supprimer-mes-donnees` (adresse lue dans la session) qui appelle `effacer_donnees_membre` (service seulement) : paiements anonymisés, jamais supprimés.
